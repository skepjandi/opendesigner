# Video Editing

> **Status: Partially implemented.** Built (video v1): videos made of **clips that show design frames**, with transitions (cut, fade, slide, dip, zoom_in), eased motion, overlay entrances and exits, a timeline view of what follows what, and a slow zoom, as undoable operations (`crates/core/src/video.rs`); **keyframes** of any number of a node over the video's time, with named moves and motion blur (`crates/core/src/animation.rs`); **3D devices** with a capture or a recording on their screen (`crates/core/src/device3d.rs`, `od_render::three_d`); a renderer that draws any moment (`od_render::video`); encoding to H.264 MP4 by running `ffmpeg` (`crates/media`); one **sound track** per video (file, start, volume, fades), mixed into the export; MCP tools `list_videos`, `render_video_frame`, `video_contact_sheet`, `animate_preset`, `export_video`, `list_video_presets`, `search_sounds`, `import_sound`, `list_sounds` (Freesound, see [Finding sounds](#finding-sounds-freesound)); CLI `videos`, `animate`, `export-video`, `video-presets`; Apple app-preview rules (15-30 s, at most 30 fps, 886x1920 or 1920x886 for iPhone, 1200x1600 or 1600x1200 for iPad, 500 MB; read from Apple's page on 2026-11-19). Checked on macOS with Homebrew's ffmpeg 9.0.1 and its VideoToolbox H.264 encoder: a 5.4 s 886x1920 30 fps video encodes to a valid MP4 (ffprobe: h264, 162 frames). **Footage (added later the same day):** the user imports MP4/QuickTime files into the agent's memory (`media/`); a clip can play a stretch of one (`footage {file, in_ms}`) with its sound, several clips of a file make cuts, and **overlays** (a design frame with no fill is transparent) are drawn over the whole timeline for a time with fades: titles, lower thirds, call-outs. Footage is decoded by `ffmpeg` (`FootageDecoder`, one process per file playing forward), the sound of every footage clip is cut, delayed and mixed under the picture and muxed with the video copied (AAC), each clip is checked to lie inside its file, and the editor has a Video tab with a playable preview and the clip list. **Not built yet:** animated overlays (they are still pictures that fade), audio mixing controls (volume, music), speed changes, captions from speech, timeline notes pinned to a time range, selecting clips on a timeline in the window, a pinned LGPL ffmpeg bundled in the app. OpenCut and Kino facts come from their public repository and docs as read on 2026-11-19; OpenCut's rewrite is in progress, so its desktop app is a scaffold, not a reference implementation to port. The timeline design is intent.

## What videos are for here

App Store and Google Play app previews, promo and changelog clips, web hero loops, short social cuts of a feature. Short, mostly screen captures and motion graphics, rarely a multi-camera edit. That shapes scope: a precise, scriptable timeline with strong title/overlay tooling beats a full colorist.

## What OpenCut teaches

[OpenCut](https://github.com/opencut-app/opencut) ("a free and open source video editor for web, desktop, and mobile", MIT; the original TypeScript app is archived as `opencut-classic`) is mid-rewrite around ideas we share:

| OpenCut | Us |
|---------|----|
| Business logic moves into a Rust core; apps are UI shells ("the UI framework for any given app is a replaceable detail") | Same rule: [Architecture](./architecture.md#the-central-rule-the-core-is-ui-agnostic) |
| Desktop app in GPUI: `Shell` with `Browser`, `Preview`, `Inspector`, `Timeline` panels (layout 2/3 top row of 25%/50%/25%, 1/3 timeline); semantic OKLCH theme tokens | Same panel set in a Qt shell; we add the agent panel ([Qt Desktop](./qt-desktop.md#window-layout)). OpenCut's GPUI choice is the one thing we do not follow |
| `crates/media`: FFmpeg **8.1.3** pinned in `setup/ffmpeg.json` with SHA-256s and prebuilt targets (Windows/Linux x86_64 and aarch64); a Bun setup script; **shared LGPL only**, `--disable-programs --disable-network --disable-avfilter …`; CI builds prebuilts for six targets and publishes a pre-release | Same *policy*: pinned manifest, checksum-verified, LGPL shared, no network protocols. The *version* is not ours to copy: it must match the FFmpeg major that Qt Multimedia uses ([below](#qt-multimedia-and-ffmpeg)). Write the setup script in Rust (`cargo xtask`) rather than add Bun to the toolchain |
| Plugin-first architecture, an Editor API, MCP server for agents, headless mode, a scripting tab | The operation API plus MCP plus headless CLI are our v1; plugins and scripting are deferred ([Roadmap](./roadmap.md)) |
| moon + proto for monorepo and tool pinning | Plain Cargo workspace first; revisit if a non-Rust toolchain (web docs, store tooling) grows |

Caveats: the OpenCut desktop app is a scaffold (its README says it opens a maximized window with the root `Shell`; the four panels are minimal), and the project says it is not yet taking outside contributions. Treat it as a design reference and a license-compatible source (MIT) for small utilities, not as a dependency.

## What Kino teaches

[Kino](https://kino.ai) is the benchmark for agent-driven video, and its docs show the pattern we want:

- **The agent works on the same timeline the user edits.** "Ask for the cut. The agent reads your footage, makes the edit, and leaves every clip on the timeline for you to move." Clips the agent changed get a **blue outline**. Every agent edit saves a **checkpoint** you can go back to. We copy this exactly ([Document Format: history](./document-format.md#history-and-checkpoints)).
- **Projects are code-like and legible to an agent.** Kino is built on Remotion, so titles and lower thirds are code in your brand, and "Claude Code reads one like a repo". We keep the *legibility* (plain-text project files, tokens for brand) but not the *code*: documents are data ([invariant 3](../../AGENTS.md)).
- **MCP is the integration point,** one local endpoint for many agents, with skills for editing style, and a way to use a Claude or ChatGPT subscription from inside the app ([Agent Integration](./agent-integration.md)).
- **Review and chat as first-class.** Notes on the timeline, references pasted into chat, live progress cards for long jobs. We take the in-app annotation model for video: a note pinned to a time range and a canvas region.

Where we deliberately differ: local-only and open files (Kino stores footage in its cloud and has accounts, plans and credits); a design canvas in the same app, so a store set can contain video and stills; store-aware validation.

## Built: video v1

- **Model.** `Document.videos`: `Video {id, name, fps (1-60), width, height (even, 16-4096), clips}` and `Clip {id, frame, duration_ms (100-60,000), transition {kind, duration_ms, ease}, motion {scale_from, scale_to, ease}}`. Time is whole milliseconds. A transition overlaps the end of the clip before it, so a 500 ms fade makes the video 500 ms shorter than its clips; a video is at most 10 minutes and 500 clips. Stored as `videos/<id>.json` (listed in `od.toml`), like pages.
- **Footage and overlays.** `Clip.footage {file: media/<name>.mp4|mov|m4v, in_ms}` instead of `frame` (exactly one); `Video.overlays [{id (o_..), frame, start_ms, duration_ms, fade_ms, enter, exit, ease}]` drawn over the clips, entering and leaving (at most half the duration each). Operations `add_overlay`, `remove_overlay`, `set_overlay`, and `set_clip` source. Footage files enter only through the user's import (`Workspace::import_footage`, sniffed by the `ftyp`/`moov` box, 8 GB cap, never overwriting, listed apart from images so an image node cannot name a video); `list_footage` shows them to the agent.
- **Operations** (undoable, attributed, checkpointed like any edit): `create_video`, `delete_video`, `set_video` (name, fps, size, **audio**), `add_clip`, `remove_clip`, `move_clip`, `set_clip` (duration_ms, frame, transition, motion). `restore_video` and `restore_clip` are the history's own and are refused from front ends. A frame that a clip shows cannot be deleted until the clip is removed.
- **Rendering.** Each clip's frame is drawn by `render_frame` once at the scale the output needs (scaled to cover the video and cropped in the middle), then drawn with the zoom, offset and opacity of that moment: fade blends, slides push the old clip out.
- **Encoding.** `od_media` pipes raw RGBA frames to `ffmpeg` (`-f rawvideo ... -c:v <encoder> -pix_fmt yuv420p -movflags +faststart`) and moves the finished `.part` file into `exports/` only when ffmpeg exits cleanly. It prefers an encoder the OS provides: `h264_videotoolbox` (macOS), `h264_mf` (Windows), then `libopenh264`, NVENC, QSV, AMF, VAAPI, and GPL `libx264` last. It looks for `ffmpeg` in `OPENDESIGNER_FFMPEG`, next to the app (and in a bundle's `Resources`), then `PATH`; without one the error says what to install. Release build on an M2 Pro: 5.4 s of 886x1920 in 7.8 s.
- **Store rules.** `od_store::video` presets validate size, length, frame rate (before any encoding) and file size (after); a failure writes nothing and names the rule, the page and the day it was read. Not checked: H.264 profile/level, the 10-12 Mbps target, the audio track.

- **Motion.** Eases (`linear`, `ease_in`, `ease_out`, `ease_in_out` (default), `back` with a small overshoot, `spring` with a damped overshoot) shape every transition, every clip zoom and every overlay entrance. Transitions: `cut`, `fade`, `slide_left|right|up|down`, `dip` (through black), `zoom_in`. An overlay has `enter` and `exit` (`none`, `fade` (default), `slide_up|down|left|right`, `pop`, `zoom`), each taking `fade_ms`, and an `ease`. Pose per moment: offset, scale and opacity, so an entrance is the overlay's own frame moved or scaled, not a new frame.
- **Keyframes.** `Video.animations [{node, prop, keys [{at_ms, value, ease}]}]`: any number of a node (`x`, `y`, `width`, `height`, `opacity`, `corner_radius`, and on a 3D device its turn, tilt, roll, zoom, lens, light, shadow, glare and screen scroll) moves over the video's time. The operation `animate` replaces the keys of one property (an empty list removes them); the value holds before the first key and after the last. `Document::at_time` gives the document as it looks at a moment, and the renderer draws a frame that holds an animated node again for every moment it moves. Named moves (`spin`, `turntable`, `swing`, `flip_in`, `hero_reveal`, `rise_in`, `drop_in`, `float`, `push_in`, `pull_back`, `orbit`, `scroll_screen`, `fade_in`, `fade_out`, `slide_in_left`, `slide_in_right`) are written as ordinary keyframes measured from the node's designed pose: the MCP tool `animate_preset` and the CLI `animate` expand them, so a move is data the user can edit. `Video.motion_blur` (2 to 16 pictures) blends the moments across a half-frame shutter while something moves; a cut is never blurred across.
- **3D devices.** A `device3d` node in a frame is a phone, tablet, laptop or monitor drawn in perspective inside its own box (`od_render::three_d`, a CPU rasterizer with a depth buffer, supersampled anti-aliasing, a studio environment and a soft shadow). The screen takes the node's `image` (a capture) or a recording (`screen_footage`), which plays while the frame is shown. The device is turned, tilted and lit with plain properties, so the agent edits it like any other node and a video animates it with the same keyframes ([Document Format](./document-format.md#3d-devices)).
- **Sequence view.** `list_videos` returns `story`: one sentence per clip (when it starts, how it arrives and over how long, what it shows, its zoom and ease, when it ends) and per overlay (start, enter, exit, end). The window's Video tab draws the same as an editor timeline (`VideoPanel.qml`, tracks in `VideoTimeline.qml`): a transport bar (start, frame back, play/pause, frame forward, end, loop, timecode `mm:ss:ff`, zoom out/in, fit), the preview above it, a ruler whose ticks adapt to the zoom, and three labelled tracks whose headers stay put while the tracks scroll sideways: **Video** (clips as rounded blocks, footage and design frames coloured apart, with a strip of pictures taken from the cached preview once it is drawn; the stretch each transition shares with the clip before it is drawn as a marked overlap), **Overlays** (overlapping overlays stack on lanes) and **Sound** (the track from its start; there is no waveform because the app holds no audio data, and the file's own length is unknown, so the bar runs to the end of the video). A playhead crosses every track; click or drag the ruler or any track to scrub, Ctrl/Cmd + wheel or pinch to zoom around the pointer, wheel to scroll. The view fits the whole video until you zoom by hand. Picking a clip, overlay or the sound shows its properties in the Details tab (the Story tab keeps the sentences). Keys: Space, Left/Right (one frame), Home/End. Preview progress, an out-of-date preview and errors are shown over the picture; with no video the panel explains how to get one.
- **Sound track.** A video carries at most one sound track: `Video.audio {file: media/<name>.mp3|wav|m4a|aac|ogg, start_ms (0-600,000), gain (0-2, 1 by default), fade_in_ms, fade_out_ms}`. It is set with `set_video` (`prop {name: "audio", value: {...}}`; `null` takes it away), so it is an attributed, undoable, checkpointed edit like any other, and it is stored with the video in `videos/<id>.json`. The file must be a plain name in the project's `media/` folder (the same rule an image node follows), and the video's own length rules: the track never makes the video longer, it is cut at the end.
- **Mixing.** After the picture is encoded, `od_media::add_audio` mixes the sound under it in one ffmpeg pass (`atrim`, `volume`, `afade`, `adelay`, `amix`): the track's gain is a `volume` filter, its fades are `afade` in and out, and it starts at `start_ms`. The picture is copied, not re-encoded. Footage sound is mixed the same way, at volume 1 and without fades.

## Audio sources

A video's sound track is any file in `media/` named `.mp3`, `.wav`, `.m4a`, `.aac` or `.ogg`. Four ways to get one there, none of which needs the others:

- **`make_sound`** (`crates/agent/src/synth.rs`): the built-in sound maker. Kinds `click`, `pop`, `tick`, `whoosh`, `swoosh_up`, `swoosh_down`, `riser`, `hit` (alias `impact`), `chime`, `drone` (alias `pad`; loops without a seam), `beat` (kick on every beat, hat between; `bpm` 40-240 and `bars`) and `stinger` (2 or 3 notes). Arguments `{kind, duration_ms?, seed?, pitch_hz?, bpm?, bars?, stereo?, name?}`. Pure Rust, no dependency: sines, noise, filters and envelopes, written as 16-bit PCM WAV at 44.1 kHz into `media/<name>.wav` with `media/<name>.synth.json` beside it (kind, seed, "synthesized, no third-party licence"). Every sound is normalized to a peak of 0.89 (about -1 dBFS), starts and ends at exactly zero after a short fade (2 ms for the drone, 8 ms otherwise), and is deterministic for a given kind, length, pitch and seed. It makes effects and simple loops, not music or speech.
- **`search_sounds` / `import_sound`**: Freesound, below. Needs the user's token; music beds are better from here.
- **`import_file` with an audio file** (`find_files` `kind: "audio"`): copies the user's own `.mp3 .wav .m4a .aac .ogg` into `media/`. The first bytes must match the extension (`ID3` or an MPEG frame for mp3, `RIFF…WAVE`, `ftyp` with an audio brand `M4A `/`M4B ` for m4a, an ADTS header for aac, `OggS`); a video container renamed `.m4a` is refused. Up to 512 MB, never overwritten, never modified.
- **A voice-over** from a speech MCP server the user added in the Connect tab (for example `minimax-mcp`), imported with `import_file` once it exists on disk.

`list_sounds` lists everything audio in `media/`: file, size, length (when ffmpeg is installed), `source` (`synthesized`, `freesound` or `imported`) and, for Freesound sounds, the attribution line. Any of them is set with `set_video` `audio`. The skill's *Sound* sections give the craft: a bed under a voice at gain 0.15 to 0.3, fades of 300 to 800 ms, hits on cuts, silence as a tool, never a silent video unless asked.

## Assets in a video

The bundled icons, generated pictures and pack art (`search_assets`, `make_asset`, `import_asset`; [Store Assets](./store-assets.md#asset-packs-icons-shapes-backgrounds-sounds)) are PNGs in `media/`. They reach a video through the same typed ops as any picture: an `image` node (`image: media/<file>`) in a design frame, and the frame is a clip or an overlay. Sounds from `import_asset` or `make_sound` are the track set with `set_video` `audio`. The `video` playbook tells the agent to take inventory (`list_media`, `list_footage`, `list_sounds`, `search_assets`) before building.

## Finding sounds: Freesound

The agent can put music and sound effects on a video. It finds them on [Freesound](https://freesound.org), a library of Creative Commons sounds, through its API v2 (`crates/agent/src/freesound.rs`).

- **The user's token.** Freesound asks every caller for a free API token, which the user gets at <https://freesound.org/apiv2/apply/> and pastes into the Connect tab. It is stored in the per-user config folder as `freesound/token` (readable by the user only) and sent only to freesound.org, in the query string where the API documents it. No agent can write it: the tools refuse with a message that says what to do ("no Freesound token: ask the user to add one in the Connect tab; they can get one at https://freesound.org/apiv2/apply/"). The token never goes into a project, an export or a log.
- **The tools.** `search_sounds {query, duration_max_ms?, page?}` lists sounds (id, name, length, license, author, a preview to listen to); `import_sound {id, name?}` downloads the preview mp3 into the project's `media/` folder and writes `media/<name>.freesound.json` beside it (id, title, author, license, license url, source url); `list_sounds` shows what is already imported. Nothing is overwritten: a free name is found instead.
- **The preview, not the original.** The file that comes down is Freesound's mp3 preview (about 128 kbit/s), because the original needs the user's own OAuth token. A video that needs the original recording has to be brought in by the user.
- **The license is the author's.** Freesound hosts sounds under many licenses (CC0, attribution, attribution noncommercial). The license travels with the sound: the tool's answer and the sidecar say which one it is, and the attribution line ("Title by Author, License, https://freesound.org/s/<id>/") is what the user has to show wherever the sound is used. The tool descriptions tell the agent this; the app's Video tab repeats it. We do not relicense anything.
- **The client.** `crates/agent/src/http.rs` is a small HTTP/1.1 client written for this: one `GET`, one answer, a connect and a read timeout, a cap on the answer's size, and a redirect that may only lead to the same site as the request that started it. The secure channel is `rustls` with the root certificates the operating system trusts. Nothing else in the app reaches the network.

### Preview in the Video tab

Play in the Video tab plays a **cached preview**, not a live render. When a video is shown (or chosen, or changed) a worker thread draws every picture of it from a detached copy of the project (`od_agent::video_preview`, the same copy `export_video` uses), one picture after the other so footage is decoded as a stream. The window shows "Preparing preview N%"; Play starts once the first second is drawn and keeps going while the playhead stays behind the drawn pictures (it shows "Buffering" and waits when it catches up). The video loops at its end.

How the preview stays cheap:

- **Pictures are kept by what they were made from.** `od_agent::preview_key` gives every moment a key: the video's settings, the clips and overlays on screen with the design frames they show, the animations, the colour tokens and the project's media files (as the file stores them, so a field added to a clip later is in the key without touching the code). The renderer's own `signature` says when two moments of one video look alike; the key also says what they look like. After an edit only the pictures whose key changed are drawn again; the rest are taken from the preview being replaced (`Preview::reusable`).
- **A picture that holds still is drawn once** and shared (`VideoRenderer::signature`).
- **The size and the rate follow the machine.** `od_agent::preview_tier` tries the longest sides 360, 540, 720 and 960 px at 15 fps or the video's own rate, and takes the best tier whose pictures fit the memory cap and can be drawn in a share of the video's length. The first preview measures the machine (three pictures) and hands the estimate to the next one, so a fast machine gets a sharp, smooth preview and a slow one a small, cheap one.
- **Pictures are kept run-length coded**, not as PNG (`od_agent::preview_frames`): a flat design frame shrinks by more than ten times, and a picture that does not shrink (footage) stays raw. Qt reads the raw pixels through the same image provider the canvas uses.
- **The sound is mixed once.** The footage clips' own sound and the sound track are mixed into a WAV (`od_media::mix_wav`, the same pieces and the same graph the export mixes) and played by Qt Multimedia (`MediaPlayer` and `AudioOutput`). The mix is named by what went into it, so an edit that leaves the sound alone does not mix again.

Limits, stated in the panel too:

- **Sharp and smooth, within the cap:** the tier is chosen as above; the exported MP4 is full size at the video's rate.
- **With sound:** the mixed WAV is played; a video with no sound says so, and a machine without `ffmpeg` says the sound could not be mixed.
- **Bounded memory:** about 256 MiB of pictures; a picture shown more than once is counted once. At the cap the preview keeps what it has and the panel says so.
- **Repaired, not cancelled, on change:** any change to the project (the log grows: the user's edit, an agent's, undo) makes the cache stale; the new preview takes the pictures the edit left alone and draws the rest. Switching video or closing the panel cancels it too. While the cache is not there yet, scrubbing draws the one picture asked for on demand.
- **The playhead follows the sound.** Two clocks run, the wall clock and the sound player's position. `app::preview::step` decides each tick: the player's position is the reference and the playhead leans toward it by a tenth of a tick (so a player that reports its position in coarse steps does not make the picture step), and when the two are more than 150 ms apart (after a stall, a seek or a loop) the player is moved to the playhead, which is right.

## Timeline model (intended)

- A **composition** page has an ordered list of tracks (video, audio, overlay, text), each holding clips with `start`, `duration`, `source in/out`, transform, effects and keyframes. Clips are nodes with stable ids, so the operation set is the same family as design operations plus `trim`, `split`, `retime`, `ripple`.
- A composition is also a **frame**: a video page can embed design frames as overlay clips (a device frame around a screen recording, a headline card), rendered by `render`.
- Time is an integer count of ticks per second (rational, never float seconds) so edits do not drift.
- Preview decodes through `media` (or Qt Multimedia for plain playback, see below) to frames shown in the preview panel at the project frame rate; scrubbing prioritizes latency (nearest keyframe plus decode forward) over exactness, with an exact frame on pause.
- Export encodes H.264/HEVC/ProRes where the platform allows, plus VP9/AV1 where the LGPL build includes them; presets for App Store app previews and Play promo video sit beside the image presets ([Store Assets](./store-assets.md)), with their own validation (resolution, frame rate, duration, size limits) `[INFERENCE: rules to be collected from Apple and Google docs in Phase 5]`.

## Qt Multimedia and FFmpeg

Read from Qt 6.12's Qt Multimedia docs: it is LGPLv3 (or GPLv2) and its **default backend is built on FFmpeg** on every platform except WebAssembly and embedded Linux. The binary packages link FFmpeg (9.0.1 in the 6.12 docs) *dynamically*; an application either bundles those libraries or depends on the system's, and may deploy **its own FFmpeg build provided the major version matches the one Qt uses**. Qt's prebuilt FFmpeg includes only features under permissive licenses. Native backends (AVFoundation on macOS; Windows Media Foundation, deprecated since Qt 6.10) are kept with limited support, and new features land only in the FFmpeg backend. Qt's docs warn that codec and hardware-acceleration behavior differs per platform, and that H.264 and similar codecs may carry patent royalties the Qt license does not cover (a distribution decision for the Phase 7 release work).

What follows for us:

- **One FFmpeg in the process** ([invariant 10](../../AGENTS.md)). Our `media` crate and Qt's backend must share the same major version; if we ship our own FFmpeg build, Qt loads it too. OpenCut's pin (8.1.3) is a different major than Qt's, so it is not directly reusable.
- **Use Qt Multimedia for what it is good at** (plain playback, audio output, `QVideoSink` access to decoded frames, `QVideoFrameInput` to feed frames in) and our `media` crate for what an editor needs (frame-accurate decode, export, thumbnails, waveforms). Where they overlap, pick one in the Phase 0 video spike and delete the other path.
- **Do not depend on the deprecated native backends.**

What the app does with it (built, 2026-11-20): the preview's sound is a WAV that `od_media` mixes with the user's own `ffmpeg` and Qt Multimedia plays; nothing of ours is decoded by Qt, so no backend is chosen by us and the app does not need Qt's FFmpeg libraries. `crates/app/build.rs` links `Multimedia` (LGPLv3, checked in [Qt Desktop](./qt-desktop.md#licensing)) and `scripts/package-macos.sh` refuses a bundle that carries Qt's FFmpeg libraries, which would be a GPL build.
